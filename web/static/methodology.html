1. ปัญหาที่ระบบนี้แก้ / แนวคิดหลัก

ผู้ใช้ไฟบางรายยังไม่มีมิเตอร์ AMR (มิเตอร์อัตโนมัติที่วัดค่าไฟรายช่วงเวลาได้จริง) — กฟภ. จึงไม่มีข้อมูล "รูปแบบการใช้ไฟจริง" ของรายนั้นเลย ระบบนี้จึง ประมาณการ โปรไฟล์การใช้ไฟ 3 ช่วง (Peak / Off-Peak / Holiday) ให้แทน โดยอ้างอิงจาก ค่าเฉลี่ยการใช้ไฟจริงของผู้ใช้ไฟรายอื่นที่ประกอบธุรกิจ+ใช้อัตราเดียวกัน (ข้อมูลที่นำเข้าจาก AMR จริงของบัญชีอื่นที่มีมิเตอร์อยู่แล้ว) แนวคิดคือ "ธุรกิจประเภทเดียวกัน มักมีรูปแบบการใช้ไฟฟ้าคล้ายกัน" — ยิ่งมีข้อมูลจริงสะสมมาก ยิ่งพยากรณ์แม่นขึ้นเรื่อยๆ โดยไม่ต้องรอให้ทุกรายติดตั้ง AMR ก่อน

2. ตรรกะจับคู่โปรไฟล์ — 6 ระดับความแม่นยำ

เวลาพยากรณ์ ระบบจะหาโปรไฟล์อ้างอิงที่ "ใกล้เคียงที่สุดเท่าที่มีข้อมูลจริงรองรับ" ตาม ลำดับนี้เสมอ (แม่นสุดก่อน ตกลงมาทีละขั้นถ้าไม่มีข้อมูล) — ผลลัพธ์ทุกครั้งจะบอกด้วยว่า จับคู่ได้ระดับไหน ไม่มีการปิดบังว่าเป็นค่าประมาณการ:

ระดับเงื่อนไขความหมาย
EXACT ตรงประเภทธุรกิจ + อัตรา + สถานะ Solar (ถ้าทราบ) แม่นยำที่สุด — มีข้อมูลจริงของคู่นี้เป๊ะๆ
SOLAR_MISMATCH ตรงธุรกิจ+อัตรา แต่ไม่มีโปรไฟล์ของสถานะ Solar ที่ตรงกัน ยังดีกว่าตกไปธุรกิจอื่น — แค่สถานะ Solar ไม่ตรง
BUSINESS_ONLY ตรงประเภทธุรกิจ แต่ไม่ตรง/ไม่ทราบอัตรา ใช้รูปแบบการใช้ไฟของธุรกิจเดียวกัน อัตราต่างออกไป
DIVISION_ONLY ไม่มีข้อมูลธุรกิจนี้ตรงๆ แต่มีธุรกิจอื่นใน TSIC division เดียวกัน ยังอยู่กลุ่มอุตสาหกรรมเดียวกัน (ต้องรู้ TSIC division ของทั้งสองฝั่ง)
RATE_ONLY ไม่ทราบ/ไม่ตรงธุรกิจ แต่ตรงประเภทอัตรา ประมาณการหยาบจากอัตราเดียวกันเท่านั้น
DEFAULT ไม่พบข้อมูลที่ตรงกันเลย ใช้ค่ากลางของระบบ (ประมาณการหยาบที่สุด)

โค้ดจริงอยู่ที่ src/amr_mapping/mapping.py ฟังก์ชัน find_load_profile() — สถานะ Solar (has_solar) มีผลแค่ชั้น EXACT เท่านั้น ชั้นที่ประมาณการอยู่แล้วไม่กรอง Solar ซ้อนเพิ่ม เพราะความแม่นยำต่ำอยู่ แล้วการกรองซ้อนจะยิ่งลดตัวเลือกโดยไม่ได้ช่วยอะไร

3. การปรับสเกลตามขนาดสัญญา (KVA)

จับคู่โปรไฟล์ได้แล้ว (ข้อ 2) ยังไม่จบ — ค่าเฉลี่ยดิบที่ได้มาอาจมาจากธุรกิจขนาดเล็ก/ใหญ่ กว่าลูกค้ารายที่กำลังพยากรณ์ จึงปรับสเกลตามอัตราส่วน KVA ตามสัญญาของลูกค้า เทียบ กับ KVA เฉลี่ยของกลุ่มอ้างอิง (contract_kva_ref):

  • ทราบ KVA ทั้งคู่ → scale_factor = contract_kva ลูกค้า ÷ contract_kva_ref ของโปรไฟล์ คูณเข้ากับค่า Demand/Energy ทุกช่วงเวลา
  • ลูกค้าทราบ KVA แต่โปรไฟล์ไม่มี KVA อ้างอิง → ใช้ scale_factor = 1.0 (ไม่ปรับ) พร้อมคำเตือน
  • ไม่ทราบ KVA ของลูกค้าเลย → ใช้ scale_factor = 1.0 เช่นกัน พร้อมคำเตือน (ปกติมากในโหมดพยากรณ์แบบไม่บันทึกข้อมูล เพราะ KVA เป็นช่องไม่บังคับกรอก)

โค้ดจริงอยู่ที่ estimate_customer_load() ในไฟล์เดียวกัน

4. "โมเดล" ที่ใช้จริงในระบบ

4.1 ค่าเฉลี่ยกลุ่ม (group averaging) — โมเดลหลักของระบบทั้งหมด ไม่ซับซ้อน ตรงไปตรงมา และเหมาะกับขนาดข้อมูลปัจจุบัน (แต่ละกลุ่มธุรกิจ+อัตรามีตัวอย่างจริงแค่หลัก สิบ) — โปร่งใส อธิบายได้ทุกตัวเลข ไม่มี "กล่องดำ" ให้สงสัย

4.2 k-means clustering (src/amr_mapping/clustering.py) — ใช้ตอน ไม่มีธุรกิจที่ตรงกับ TSIC division เป๊ะเลย จัดกลุ่มธุรกิจที่มีข้อมูลจริงตาม "รูปแบบการ ใช้ไฟ" (shape vector — สัดส่วนการใช้ไฟแต่ละชั่วโมงจาก 24 ชม. ให้ผลรวมเป็น 1.0 เพื่อเทียบ รูปแบบได้โดยไม่ติดเรื่องขนาดธุรกิจ) แล้วเสนอตัวแทนของกลุ่มที่พบบ่อยที่สุดเป็นค่าประมาณ การขั้นสุดท้ายก่อนตกไปที่ DEFAULT — เขียนเองแบบง่าย (farthest-first init + Lloyd's algorithm) ไม่ใช้ไลบรารีหนักอย่าง scikit-learn เพราะข้อมูลมีน้อยและไม่คุ้มเพิ่ม dependency ใหญ่ขนาดนั้น

4.3 การจับคู่ TSIC (nearest_business_type_by_tsic / rank_business_types_by_tsic) — เวลาค้นหาประเภทธุรกิจจากชื่อบริษัทได้ รหัส TSIC มา แต่ในระบบยังไม่มีธุรกิจที่ตรง division เป๊ะ จะหาธุรกิจอื่นที่อยู่ TSIC section เดียวกันก่อน (เรียงตาม division ใกล้เคียงสุด) ถ้าไม่มีเลยค่อย fallback ไปใช้ ตัวแทนกลุ่ม k-means (ข้อ 4.2) — ฟังก์ชัน "rank_" คืนได้หลายอันดับ (1/2/3) ให้ผู้ใช้เลือก เองแทนการ auto-apply แบบมั่นใจเกินจริงตัวเดียว

4.4 การจับคำสำคัญ (keyword matching) (src/amr_mapping/keyword_classify.py) — ใช้ตอนมีแค่ข้อความอิสระ (เช่น สรุปจาก Wikipedia) ไม่มีรหัส TSIC มาด้วยเลย สแกนหาคำ ที่รู้จัก (เช่น "โรงแรม", "ร้านสะดวกซื้อ") แล้วแปลงเป็น TSIC division คร่าวๆ — เป็นการ จับคู่คำตรงตัวธรรมดา ไม่ใช่ AI/NLP ใดๆ ทั้งสิ้น จึงต้องบอกผู้ใช้ชัดเจนเสมอว่าเป็น การเดา ไม่ใช่ข้อมูลทางการ

5. ทำไมยังไม่ใช้ Machine Learning เต็มรูปแบบ

เคยพิจารณาแล้วว่าจะใช้โมเดล ML (regression/neural network) พยากรณ์ตัวเลข kW/kWh โดยตรงแทนค่าเฉลี่ยกลุ่ม แต่ข้อมูลจริงตอนนี้ยังน้อยเกินไป — แต่ละประเภทธุรกิจมี ตัวอย่างจริงแค่หลักสิบ (บางกลุ่ม 11-14 ตัวอย่าง) ซึ่งน้อยกว่าที่โมเดล ML ทั่วไปต้องการ มากเพื่อเรียนรู้ได้แม่นจริงโดยไม่ "จำข้อมูลผิดๆ" (overfit) — ยิ่งโมเดลซับซ้อนขึ้นเท่าไหร่ ยิ่งต้องการข้อมูลมากขึ้นเท่านั้น ด้วยขนาดข้อมูลปัจจุบัน ค่าเฉลี่ยกลุ่มธรรมดา (ข้อ 4.1) เป็นตัวประมาณการที่เหมาะสมและน่าเชื่อถือกว่า

แผนในอนาคต: เมื่อมีข้อมูล AMR จริงสะสมมากพอ (หลักร้อยตัวอย่างขึ้นไปต่อประเภทธุรกิจ) ค่อยพิจารณาโมเดล regression ที่คำนึงถึงหลายปัจจัยพร้อมกัน (ธุรกิจ, ฤดูกาล, KVA ฯลฯ) — ไม่ใช่ตอนนี้

6. ห่วงโซ่การค้นหาประเภทธุรกิจอัตโนมัติ (5 ชั้น)

ปุ่ม "ค้นหาประเภทธุรกิจอัตโนมัติ" พิมพ์แค่ชื่อบริษัทแล้วให้ระบบหา TSIC/ประเภทธุรกิจให้ เอง — ลองหลายแหล่งข้อมูลตามลำดับ เพราะแต่ละแหล่งมีข้อจำกัดต่างกัน:

  1. DBD DataWarehouse (เว็บทางการของกรมพัฒนาธุรกิจการค้า) — แม่นยำสุด (รหัส TSIC จริง) แต่มักโดนระบบป้องกันบอท (Incapsula) บล็อก ไม่ใช่ว่าไม่พบบริษัทนี้จริงๆ
  2. dataforthai.com (เว็บบุคคลที่สาม) — ถ้า DBD บล็อก ลองเว็บนี้แทน ได้แค่ "หมวดธุรกิจ" เป็นข้อความอิสระ ไม่ใช่รหัส TSIC
  3. ฐานข้อมูล DBD Open Data ในเครื่อง — ข้อมูลเปิดของ DBD เอง (ไม่มีระบบกันบอท) ดึงมาเก็บไว้ล่วงหน้าผ่านหน้า Admin แต่ครอบคลุมเฉพาะบริษัทที่ "ตั้งใหม่/เลิกกิจการ" ตั้งแต่ปี 2020 เท่านั้น ไม่ใช่ทะเบียนเต็ม — มีรหัสวัตถุประสงค์ (คล้าย TSIC) ติดมาด้วย จึงจับคู่ประเภทธุรกิจอัตโนมัติได้แม่นถ้าเจอชื่อตรงเป๊ะ
  4. Wikipedia (ฟรี ไม่มีค่าใช้จ่าย) — ช่วยเฉพาะบริษัทใหญ่/มีชื่อเสียงที่มักไม่อยู่ในข้อ 3 พอดี (เพราะเป็นบริษัทเก่า) ใช้การจับคำสำคัญ (ข้อ 4.4) เดาประเภทธุรกิจจากข้อความสรุป
  5. เลือกเอง — ถ้าทุกแหล่งหาไม่เจอ/ไม่มั่นใจพอ ระบบจะแสดงตัวเลือกที่ใกล้เคียงที่สุด (สูงสุด 3 อันดับ) ให้เลือกเอง แทนการเดาแบบเงียบๆ ที่อาจผิดได้

ทุกชั้นที่เป็นการ "เดา" (ไม่ใช่รหัส TSIC จริงจากข้อ 1/3) จะถูกทำเครื่องหมายชัดเจนว่าเป็น ค่าประมาณการเสมอ ไม่เนียนว่าเป็นข้อมูลยืนยันแล้ว — และระบบจะไม่พยายามเลี่ยง/ข้าม ระบบป้องกันบอทของเว็บใดๆ เด็ดขาด ถ้าโดนบล็อกจะแจ้งตรงๆ แล้วลองแหล่งถัดไปแทน

7. ขั้นตอนการใช้งานทีละขั้น

โหมด "พยากรณ์แบบไม่บันทึกข้อมูล" (หน้าแรก)

  1. พิมพ์ชื่อบริษัท (ไม่บังคับ ใช้แสดงผลเท่านั้น ไม่ส่งไปที่ไหน)
  2. กด "🔍 ค้นหาประเภทธุรกิจอัตโนมัติ" (ไม่บังคับ) — ถ้าจับคู่ได้แบบมั่นใจ จะตั้งประเภทธุรกิจ + พยากรณ์ให้ทันที
  3. ถ้าไม่มั่นใจพอ ระบบจะให้เลือกจากตัวเลือกอันดับ 1/2/3 หรือพี่เลือกประเภทธุรกิจ/รหัสอัตราเองจาก dropdown ก็ได้เสมอ
  4. กรอก KVA ตามสัญญา/สถานะ Solar เพิ่มเติมได้ (ไม่บังคับ) แล้วกด "พยากรณ์" (หรือปล่อยให้ระบบพยากรณ์อัตโนมัติหลังเลือกประเภทธุรกิจ)
  5. ดูผล แล้วกด "📥 ดาวน์โหลด Excel" เพื่อเก็บ/ส่งรายงานได้

โหมด "ค้นหาในทะเบียนลูกค้า" (หน้าแรก)

  1. พิมพ์เลขบัญชีผู้ใช้ไฟที่เคยลงทะเบียนไว้แล้ว (customers.csv/customers_local.csv)
  2. กด "ค้นหา" — ระบบดึงประเภทธุรกิจ/อัตรา/KVA ของบัญชีนั้นมาพยากรณ์ให้อัตโนมัติ

นำเข้า AMR จริง (หน้า Admin)

  1. เลือกโหมด "ดึงจากเว็บ PEA" (กรอก username/password + ช่วงวันที่) หรือ "แนบไฟล์ที่มีอยู่แล้ว"
  2. ปล่อยให้ระบบตรวจจับประเภทธุรกิจ/อัตรา/KVA อัตโนมัติจากหน้าข้อมูลผู้ใช้ไฟของ PEA (แนะนำ) หรือกรอกเองในตัวเลือกขั้นสูง
  3. กด "ดาวน์โหลดและนำเข้า" — ข้อมูลเฉลี่ยแบบไม่ระบุตัวตนจะถูกบันทึกลง load_profiles.csv/load_curves.csv (ยิ่งนำเข้าเยอะ ยิ่งพยากรณ์แม่นขึ้น — ดูข้อ 5)
  4. ดูผ่าน "หมวดหมู่ธุรกิจทั้งหมดในระบบ" ว่าประเภทไหนมีข้อมูลจริงรองรับแล้วบ้าง
  5. (ไม่บังคับ) กด "ดึงข้อมูล DBD Open Data มาเก็บในเครื่อง" เป็นระยะ เพื่อให้ข้อจำกัดในข้อ 6.3 ทันสมัยที่สุด
